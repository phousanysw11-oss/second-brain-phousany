# เกณฑ์เริ่มต้นและข้อมูลสำหรับตัวคำนวณ

แบบประยุกต์ที่ Phou อนุมัติในบทสนทนา 12 กันยายน 2026 ไม่ใช่สูตร ICE ต้นฉบับ และไม่ใช่แบบจำลองผลประหยัดที่ผ่านการพิสูจน์

| ปัจจัย | 0 คะแนน | 1 คะแนน | 2 คะแนน | 3 คะแนน |
|---|---|---|---|---|
| เงินตรง/ครั้ง ไม่รวมแรงงาน (LAK) | 0 | มากกว่า 0 ถึง 100,000 | มากกว่า 100,000 ถึง 500,000 | มากกว่า 500,000 |
| นาทีคนรวม/ครั้ง | 0 | มากกว่า 0 ถึง 15 | มากกว่า 15 ถึง 60 | มากกว่า 60 |
| ผลกระทบเมื่อช้าหรือผิด | ตรวจแล้วไม่มีผลที่ระบุได้ | คนทำต้องแก้ แต่งานอื่นยังเดินต่อ | คน/ทีมอื่นหรือขั้นถัดไปรอ | กระทบลูกค้า การขาย เก็บเงิน หรือการดำเนินงานสำคัญ |
| ครั้ง/เดือน | 0 | มากกว่า 0 ถึง 4 | มากกว่า 4 ถึง 20 | มากกว่า 20 |

รวม = คะแนนเงิน + คะแนนเวลา + คะแนนผลกระทบ + คะแนนความถี่ ไม่มีการถ่วงน้ำหนักเพิ่ม ไม่คูณค่าต่อครั้งด้วยความถี่ก่อนเข้าตาราง หากต้องการรายงานยอดภาระต่อเดือนภายหลัง ให้แยกจากคะแนนและไม่เรียกยอดนั้นว่าผลประหยัด

ผลกระทบไม่ทราบต้องเว้นว่าง ไม่ใช่ระดับ 0; ทุกระดับต้องมีเหตุผล งานไม่มีครั้งเกิดไม่อยู่ในอันดับปัจจุบัน คะแนนรวมจะแสดงเฉพาะเมื่อข้อมูลครบ เพื่อให้อ่านภาระต่อกรณีได้โดยไม่จัดเป็นงานที่ต้องทำก่อน

## JSON ที่ agent เตรียมให้

ดู [ตัวอย่างรันได้](../assets/example.json) และ [ไฟล์ว่าง](../assets/blank.json)

- ระดับบน: `business` ธุรกิจเดียว, `period` ช่วงข้อมูลจริง/ฐานประมาณที่ชัดเจน, `currency` ต้องเป็น `LAK`, `tasks` รายการงาน
- งาน: `name`, `direct_cost_lak`, `cost_includes`, `human_minutes`, `impact` (จำนวนเต็ม 0–3), `impact_reason`, `frequency` และ `evidence` (แหล่งที่มา/คำบอก/ฐานประมาณ)
- `null` หรือช่องข้อความว่าง = ไม่ทราบ; ห้ามใช้ชื่อบริษัท/ช่วงเวลาที่เป็นช่องว่างมาจัดอันดับจริง
- ความถี่ใช้ **แบบเดียว**: `{"unit":"monthly","count":8}`, `{"unit":"yearly","count":1}` หรือ `{"unit":"daily","count":2,"working_days_per_month":22}` แบบปีหมายถึงค่าเฉลี่ยรายปีที่เลือกหาร 12 ไม่ใช่จำนวนจริงเฉพาะเดือนใดเดือนหนึ่ง ต้องระบุฐานใน `period` ให้เปรียบเทียบกันได้
- ไม่รับ `working_days_per_month` ในแบบเดือน/ปี เพื่อกันคูณซ้ำ วันทำงานเป็นจำนวนวันจริง 0–31; จำนวนครั้งเป็นค่าที่ไม่ติดลบและมีค่าจำกัด รองรับเศษส่วนจากการเฉลี่ย
- แหล่งที่มาไม่บังคับให้คะแนนเลขหยุด แต่ถ้าขาดจะแสดงคำเตือนว่าขาดหลักฐาน ไม่แปลว่าตัวเลขได้รับการยืนยันแล้ว
- หากใส่ `business`, `period`, `currency` ในงานซ้ำ ต้องตรงกับระดับบน มิฉะนั้นปฏิเสธแถวนั้น ไม่แปลงเงินหรือรวมช่วงเอง

## คะแนนเท่ากัน

เรียงรวมลง แล้วผลกระทบลง ถ้ายังเสมอให้ใช้อันดับร่วม (เช่น 1, 1, 3) ไม่ใช้ชื่องานหรือลำดับกรอกตัดสินคุณค่า

ตัวคำนวณรองรับหลักฐานความง่ายแบบเลือกใช้: `fix_minutes` เวลารวมคนที่คาดว่าต้องใช้เพื่อแก้งาน, `ease_evidence` เหตุผล/หลักฐาน, `ease_basis` ขอบเขตเดียวกัน เช่น “รวมสร้าง ทดสอบ ฝึกผู้ใช้ และค่าแรงดูแลเดือนแรก” ใช้เวลาน้อยก่อน **เฉพาะทุกงานในกลุ่มเสมอมีข้อมูลครบและใช้ ease_basis เดียวกัน** ถ้ามีเพียงบางงานให้คงอันดับร่วม การประมาณต้องระบุว่าเป็นประมาณ ไม่ได้พิสูจน์ความง่ายจริง

นี่เป็นตัวช่วยตัดสินเสมอ ไม่ใช่คะแนนปัจจัยที่ห้า ทางเลือกอื่นคืออธิบายหลักฐานเปรียบเทียบความง่ายในข้อเสนอโดยไม่ฝืนสร้างอันดับ

## การเปลี่ยนเกณฑ์อย่างชัดเจน

ใส่ `thresholds` ระดับบนเพียงแห่งเดียว พร้อม `threshold_reason` ที่อธิบายเหตุผล เช่น:

```json
{"thresholds":{"money":[100000,500000],"time":[15,60],"repetition":[4,20]},"threshold_reason":"คงเกณฑ์เริ่มต้นเพื่อทดลองรอบแรก"}
```

แต่ละคู่ต้องเป็นจำนวนบวก เรียงต่ำไปสูง; ไม่รับเกณฑ์รายงานเพื่อกันเปรียบเทียบคนละกติกา ค่า 0 และผลกระทบยังใช้ความหมายเดิม ผลลัพธ์เก็บเกณฑ์ที่ใช้และเหตุผลไว้ทุกครั้ง
